# S-11 · `decide_practice_strategy` — 조회와 연습 전략 선택

[세부 단계 목록](README.md) · [공통 반환 계약](../05-contracts/common-result.md) · [데이터 모델](../05-contracts/data-models.md)

## 1. 단일 책임과 경계

필요한 근거를 조회하고 변경 제안을 준비하여 한 번의 코칭 계획을 생성한다.

- 실행 성격: **LLM + 제한된 도구 루프**
- 협업 담당: Agent
- 범위 제외: 계획 승인·명령 발행·UI 적용·관측 진위 판정은 담당하지 않는다.
- 상위 실행 경로: [Big Node 목록](../02-big-nodes/README.md)에서 관리한다.

## 2. 필요한 함수

진입점은 `decide_practice_strategy(request, context) -> NodeResult[CoachPlan]`로 표현한다. 다음 함수는 내부 연산이며 Agent에 자동 공개되는 도구가 아니다.

| 내부 함수 | 입력 | 반환·책임 |
| --- | --- | --- |
| call_text_model | 컨텍스트·도구 정의 | 모델 응답 |
| dispatch_read_or_stage_action | 도구 호출·범위 | 읽기 결과 또는 ActionProposal |
| update_bounded_context | 도구 결과·남은 예산 | 다음 판단 입력 |
| finalize_coach_plan | 최종 응답·제안 ID | 명시적 행동·근거·재평가 기준 |

## 3. 내부 처리 순서

1. 규칙을 반복 설명하는 것에서 끝나지 않고 필요한 정보 조회를 선택한다.
2. 변경 도구는 이 단계에서 제안만 stage하며 화면 설정을 바꾸지 않는다.
3. 유지·추가 관측·보정·연습 변경·종료 중 상황에 맞는 행동을 고른다.
4. 주요 변수를 가능하면 하나씩 바꾸고 다음 확인 기준을 지정한다.

## 4. 입력 계약

| 입력 타입 | 필수 의미 |
| --- | --- |
| CoachContext | 상태·허용 도구·예산 |
| ToolResult[] | 읽기 결과 또는 staged 제안 영수증 |
| ModelProfile | 모델·양자화·템플릿·생성 설정 |

세션·시도·시계·버전 참조는 [데이터 모델](../05-contracts/data-models.md)에 따른다. 범위가 맞지 않거나 필수 필드가 없으면 추정값으로 채우지 않는다.

## 5. 출력 계약

반환은 `NodeResult[CoachPlan]`이며 `status`, `data`, `diagnostics`, `outcome` 네 키를 사용한다.

- `data` 타입: `CoachPlan`
- 보존할 업무 필드: `decision_id, snapshot_ref, evidence_refs, action, proposal_refs, rationale, review_criteria, user_message`
- `diagnostics`는 위 내부 함수명을 키로 실행·생략·실패와 근거를 기록한다.
- 데이터의 `null`, 빈 목록, unknown은 서로 다른 의미다. [공통 결과 계약](../05-contracts/common-result.md)의 규칙을 따른다.

## 6. 업무 결과와 오류

| outcome | 업무상 의미 |
| --- | --- |
| plan_ready | 검증 대상으로 전달할 계획 |
| observe_more | 정보 부족으로 추가 연습·관측 제안 |
| keep_current | 변경 없이 유지 |
| model_unavailable | 모델 실행 실패·예산 소진 |

`outcome`은 `status`와 다른 축이다. 정상적으로 보류·빈 결과·정보 부족을 판단했으면 `status=success`일 수 있다. 실제 필수 처리 실패는 `status=error`로 구분하고, 안전한 일부 산출물이 있을 때만 `partial`을 사용한다. 예외를 잡았다는 이유로 성공으로 바꾸지 않는다.

재시도 가능성은 진단 힌트로 반환하며, 실제 재시도·다음 단계 선택은 하네스가 판단한다. 대기나 비동기 실행을 실행 오류와 혼동하지 않는다.

## 7. 검증 사례

- 조회 결과에 없는 오류·음 길이·원인을 만들지 않는다.
- 조회 뒤 부족한 정보가 밝혀지면 개입을 보류할 수 있다.
- 도구 호출 예산과 전체 시간 예산을 넘지 않는다.
- staged 결과를 applied로 설명하지 않는다.

## 8. 설계 검토 항목

- 필드 타입·단위·버전과 유효 구간을 팀 계약에 맞춰 고정한다.
- 실행 한도·정책값은 [결정 항목](../07-decision-points.md)의 측정 절차로 선택한다.
- 근거·실행 상태·보류 사유가 다음 단계에서 소실되지 않는지 확인한다.

이 문서는 구현 책임과 검증 기준을 정의하며 현재 코드·완료율·구현 진척을 기록하지 않는다.
