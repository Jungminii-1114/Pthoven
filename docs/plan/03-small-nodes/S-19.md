# S-19 · `verify_and_deliver_report` — 보고서 검증과 사용자 전달

[세부 단계 목록](README.md) · [공통 반환 계약](../05-contracts/common-result.md) · [데이터 모델](../05-contracts/data-models.md)

## 1. 단일 책임과 경계

주장·수치·범위·실행 상태를 대조하고 지지된 내용만 사용자에게 전달한다.

- 실행 성격: **규칙 검증 + 선택적 의미 검토**
- 협업 담당: 평가·서버·디자인
- 범위 제외: 사람의 실제 연주 능력·접촉 정답을 보고서 검증만으로 입증하지 않는다.
- 상위 실행 경로: [Big Node 목록](../02-big-nodes/README.md)에서 관리한다.

## 2. 필요한 함수

진입점은 `verify_and_deliver_report(request, context) -> NodeResult[VerifiedReport]`로 표현한다. 다음 함수는 내부 연산이며 Agent에 자동 공개되는 도구가 아니다.

| 내부 함수 | 입력 | 반환·책임 |
| --- | --- | --- |
| verify_numeric_claims | 숫자·단위·시도·근거 | 일치 여부 |
| verify_action_and_scope_claims | 명령 상태·조건·문장 | 실행·범위 정합성 |
| review_unsupported_explanations | 문장·근거 | 제외·수정·보류 목록 |
| deliver_verified_sections | 검증된 구조·화면 계약 | 사용자 보고서와 검증 상태 |

## 3. 내부 처리 순서

1. 인용 ID 존재만으로 내용이 지지된다고 판단하지 않는다.
2. 불일치 문장은 정해진 범위에서 수정하거나 생략한다.
3. 선택적 LLM 의미 검토를 사용해도 실행·수치 검증을 대체하지 않는다.
4. 누락·보류 이유와 제한된 결과를 함께 전달한다.

## 4. 입력 계약

| 입력 타입 | 필수 의미 |
| --- | --- |
| ReportDraft | 구조화 초안과 근거 |
| EvidenceBundle | 허용된 원본 기록 |
| DeliveryContext | 사용자·세션·렌더링 범위 |

세션·시도·시계·버전 참조는 [데이터 모델](../05-contracts/data-models.md)에 따른다. 범위가 맞지 않거나 필수 필드가 없으면 추정값으로 채우지 않는다.

## 5. 출력 계약

반환은 `NodeResult[VerifiedReport]`이며 `status`, `data`, `diagnostics`, `outcome` 네 키를 사용한다.

- `data` 타입: `VerifiedReport`
- 보존할 업무 필드: `report_id, verified_claims, omitted_claims, verification_findings, rendered_sections, evidence_refs, delivery_state`
- `diagnostics`는 위 내부 함수명을 키로 실행·생략·실패와 근거를 기록한다.
- 데이터의 `null`, 빈 목록, unknown은 서로 다른 의미다. [공통 결과 계약](../05-contracts/common-result.md)의 규칙을 따른다.

## 6. 업무 결과와 오류

| outcome | 업무상 의미 |
| --- | --- |
| verified | 허용 범위의 보고서 전달 |
| partially_supported | 일부 주장을 제외한 보고서 |
| withheld_report | 핵심 내용을 지지할 수 없음 |
| delivery_failed | 검증 결과와 별개인 전달 실패 |

`outcome`은 `status`와 다른 축이다. 정상적으로 보류·빈 결과·정보 부족을 판단했으면 `status=success`일 수 있다. 실제 필수 처리 실패는 `status=error`로 구분하고, 안전한 일부 산출물이 있을 때만 `partial`을 사용한다. 예외를 잡았다는 이유로 성공으로 바꾸지 않는다.

재시도 가능성은 진단 힌트로 반환하며, 실제 재시도·다음 단계 선택은 하네스가 판단한다. 대기나 비동기 실행을 실행 오류와 혼동하지 않는다.

## 7. 검증 사례

- 올바른 근거 ID에 잘못된 수치를 연결한 보고서를 거절한다.
- changed_conditions를 동일 조건 향상으로 바꾼 문장을 잡는다.
- 최종 점수 하나로 unknown 구간을 숨기지 않는다.
- 검증 성공과 화면 전달 성공을 별도로 기록한다.

## 8. 설계 검토 항목

- 필드 타입·단위·버전과 유효 구간을 팀 계약에 맞춰 고정한다.
- 실행 한도·정책값은 [결정 항목](../07-decision-points.md)의 측정 절차로 선택한다.
- 근거·실행 상태·보류 사유가 다음 단계에서 소실되지 않는지 확인한다.

이 문서는 구현 책임과 검증 기준을 정의하며 현재 코드·완료율·구현 진척을 기록하지 않는다.
