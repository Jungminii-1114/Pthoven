# S-13 · `issue_practice_command` — 변경 묶음 발행과 대기 상태 기록

[세부 단계 목록](README.md) · [공통 반환 계약](../05-contracts/common-result.md) · [데이터 모델](../05-contracts/data-models.md)

## 1. 단일 책임과 경계

검증된 변경 묶음을 한 번만 발행하고 적용을 기다리는 실행 기록을 만든다.

- 실행 성격: **결정론적**
- 협업 담당: 서버
- 범위 제외: 클라이언트 실제 적용과 성공 판정은 하지 않는다.
- 상위 실행 경로: [Big Node 목록](../02-big-nodes/README.md)에서 관리한다.

## 2. 필요한 함수

진입점은 `issue_practice_command(request, context) -> NodeResult[CommandTicket]`로 표현한다. 다음 함수는 내부 연산이며 Agent에 자동 공개되는 도구가 아니다.

| 내부 함수 | 입력 | 반환·책임 |
| --- | --- | --- |
| reserve_idempotency_key | 세션·계획·시도 | 중복 발행 방지 |
| persist_pending_ticket | 검증된 변경 묶음 | 영속 또는 복구 가능한 queued 기록 |
| publish_command_ticket | 클라이언트 연결·명령 | 전달 시도와 전송 상태 |
| track_ack_deadline | 명령·시간 예산 | 재조정 시점 |

## 3. 내부 처리 순서

1. 여러 설정 제안은 하나의 change_set으로 검증·발행한다.
2. 한 세션의 동시 대기 변경을 제어한다.
3. 발행·전달만으로 실제 설정 버전을 올리지 않는다.
4. 타임아웃 시 적용 안 됨으로 단정하지 않고 상태 조정을 시작한다.

## 4. 입력 계약

| 입력 타입 | 필수 의미 |
| --- | --- |
| ValidatedPlan | 검증된 change_set·전제 조건 |
| CommandJournal | 중복 키·대기 명령·세션 상태 |

세션·시도·시계·버전 참조는 [데이터 모델](../05-contracts/data-models.md)에 따른다. 범위가 맞지 않거나 필수 필드가 없으면 추정값으로 채우지 않는다.

## 5. 출력 계약

반환은 `NodeResult[CommandTicket]`이며 `status`, `data`, `diagnostics`, `outcome` 네 키를 사용한다.

- `data` 타입: `CommandTicket`
- 보존할 업무 필드: `command_id, decision_id, change_set, expected_versions, command_epoch, apply_at, deadline, lifecycle=queued`
- `diagnostics`는 위 내부 함수명을 키로 실행·생략·실패와 근거를 기록한다.
- 데이터의 `null`, 빈 목록, unknown은 서로 다른 의미다. [공통 결과 계약](../05-contracts/common-result.md)의 규칙을 따른다.

## 6. 업무 결과와 오류

| outcome | 업무상 의미 |
| --- | --- |
| queued | 적용 대기 |
| duplicate_ticket | 기존 동일 명령 반환 |
| pending_conflict | 기존 명령 처리 대기 |
| dispatch_failed | 전달 실패 |

`outcome`은 `status`와 다른 축이다. 정상적으로 보류·빈 결과·정보 부족을 판단했으면 `status=success`일 수 있다. 실제 필수 처리 실패는 `status=error`로 구분하고, 안전한 일부 산출물이 있을 때만 `partial`을 사용한다. 예외를 잡았다는 이유로 성공으로 바꾸지 않는다.

재시도 가능성은 진단 힌트로 반환하며, 실제 재시도·다음 단계 선택은 하네스가 판단한다. 대기나 비동기 실행을 실행 오류와 혼동하지 않는다.

## 7. 검증 사례

- 같은 계획 재시도에 새 명령을 계속 만들지 않는다.
- 전송 직후 applied로 기록하지 않는다.
- 대기 기록 생성과 전송 실패를 구분한다.
- 서버 재시작 후 대기 상태를 재조정할 수 있다.

## 8. 설계 검토 항목

- 필드 타입·단위·버전과 유효 구간을 팀 계약에 맞춰 고정한다.
- 실행 한도·정책값은 [결정 항목](../07-decision-points.md)의 측정 절차로 선택한다.
- 근거·실행 상태·보류 사유가 다음 단계에서 소실되지 않는지 확인한다.

이 문서는 구현 책임과 검증 기준을 정의하며 현재 코드·완료율·구현 진척을 기록하지 않는다.
