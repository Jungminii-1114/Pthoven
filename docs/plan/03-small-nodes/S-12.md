# S-12 · `validate_coach_plan` — 계획·근거·변경 조건 검증

[세부 단계 목록](README.md) · [공통 반환 계약](../05-contracts/common-result.md) · [데이터 모델](../05-contracts/data-models.md)

## 1. 단일 책임과 경계

계획 형식·근거·도구 범위·현재 상태를 검사하고 실행 가능한 변경 묶음을 확정한다.

- 실행 성격: **결정론적 우선**
- 협업 담당: Agent·서버
- 범위 제외: 임의로 더 쉬운 전략으로 바꿔 승인하거나 실제 명령을 적용하지 않는다.
- 상위 실행 경로: [Big Node 목록](../02-big-nodes/README.md)에서 관리한다.

## 2. 필요한 함수

진입점은 `validate_coach_plan(request, context) -> NodeResult[ValidatedPlan]`로 표현한다. 다음 함수는 내부 연산이며 Agent에 자동 공개되는 도구가 아니다.

| 내부 함수 | 입력 | 반환·책임 |
| --- | --- | --- |
| validate_plan_schema | 계획·스키마 | 형식 오류 |
| verify_evidence_bindings | 주장·근거 ID | 값·출처·범위 검사 |
| validate_projected_config | 변경 묶음·실제 설정 | 최종 설정의 유효성 |
| check_control_preconditions | 버전·단계·epoch | 오래된 판단·충돌 검사 |

## 3. 내부 처리 순서

1. 정확한 스키마와 실제 등록된 도구만 허용한다.
2. 동일 설정을 바꾸는 상충 제안과 pause/resume·finish 혼합을 거절한다.
3. 가용 샘플 부족을 수치 0으로 바꾸거나 관측 임계값을 완화하는 계획을 거절한다.
4. 검증은 문장 형식과 실제 사실·행동 제약을 별도로 확인한다.

## 4. 입력 계약

| 입력 타입 | 필수 의미 |
| --- | --- |
| CoachPlan | 계획·staged 제안·재평가 기준 |
| LiveControlState | 세션 단계·실제 설정·보정·epoch |
| EvidenceIndex | 접근 가능한 근거 |
| ActionPolicy | 도구·인자·변경 한도 |

세션·시도·시계·버전 참조는 [데이터 모델](../05-contracts/data-models.md)에 따른다. 범위가 맞지 않거나 필수 필드가 없으면 추정값으로 채우지 않는다.

## 5. 출력 계약

반환은 `NodeResult[ValidatedPlan]`이며 `status`, `data`, `diagnostics`, `outcome` 네 키를 사용한다.

- `data` 타입: `ValidatedPlan`
- 보존할 업무 필드: `validation_id, plan_ref, change_set, expected_versions, apply_at, expires_at, validation_findings`
- `diagnostics`는 위 내부 함수명을 키로 실행·생략·실패와 근거를 기록한다.
- 데이터의 `null`, 빈 목록, unknown은 서로 다른 의미다. [공통 결과 계약](../05-contracts/common-result.md)의 규칙을 따른다.

## 6. 업무 결과와 오류

| outcome | 업무상 의미 |
| --- | --- |
| validated | 실행 가능한 계획 |
| needs_revision | 제한된 수정 요청 가능 |
| stale_plan | 조건 변경으로 재판단 필요 |
| rejected | 정책·근거·범위 위반 |

`outcome`은 `status`와 다른 축이다. 정상적으로 보류·빈 결과·정보 부족을 판단했으면 `status=success`일 수 있다. 실제 필수 처리 실패는 `status=error`로 구분하고, 안전한 일부 산출물이 있을 때만 `partial`을 사용한다. 예외를 잡았다는 이유로 성공으로 바꾸지 않는다.

재시도 가능성은 진단 힌트로 반환하며, 실제 재시도·다음 단계 선택은 하네스가 판단한다. 대기나 비동기 실행을 실행 오류와 혼동하지 않는다.

## 7. 검증 사례

- 유효한 JSON이어도 존재하지 않는 근거 ID는 거절한다.
- 사용자 수동 설정 변경 뒤 도착한 계획은 재검사한다.
- 범위 밖 BPM·음표 인덱스·힌트 단계를 거절한다.
- 모델이 contact_verified를 true로 바꾸는 요청은 허용하지 않는다.

## 8. 설계 검토 항목

- 필드 타입·단위·버전과 유효 구간을 팀 계약에 맞춰 고정한다.
- 실행 한도·정책값은 [결정 항목](../07-decision-points.md)의 측정 절차로 선택한다.
- 근거·실행 상태·보류 사유가 다음 단계에서 소실되지 않는지 확인한다.

이 문서는 구현 책임과 검증 기준을 정의하며 현재 코드·완료율·구현 진척을 기록하지 않는다.
