# S-15 · `reconcile_intervention` — 실제 적용 결과와 상태 동기화

[세부 단계 목록](README.md) · [공통 반환 계약](../05-contracts/common-result.md) · [데이터 모델](../05-contracts/data-models.md)

## 1. 단일 책임과 경계

ACK 또는 클라이언트 실제 상태를 대조해 개입 기록을 확정하거나 불명 상태로 보존한다.

- 실행 성격: **결정론적**
- 협업 담당: 서버·웹
- 범위 제외: 변경된 조건에서 점수가 오른 것을 인과 효과로 확정하지 않는다.
- 상위 실행 경로: [Big Node 목록](../02-big-nodes/README.md)에서 관리한다.

## 2. 필요한 함수

진입점은 `reconcile_intervention(request, context) -> NodeResult[InterventionRecord]`로 표현한다. 다음 함수는 내부 연산이며 Agent에 자동 공개되는 도구가 아니다.

| 내부 함수 | 입력 | 반환·책임 |
| --- | --- | --- |
| verify_ack_identity | ACK·명령·클라이언트 | 범위·명령 연결 |
| reconcile_actual_values | 요청·실제 값·버전 | 일치 또는 충돌 |
| finalize_intervention_record | 확인된 결과 | 적용·거절·불명 기록 |
| schedule_state_probe | ACK 누락·불명 상태 | 읽기 전용 실제 상태 확인 |

## 3. 내부 처리 순서

1. 전송 실패·ACK 누락을 미적용과 동일시하지 않는다.
2. 불명 상태가 풀리기 전 상충하는 새 명령을 발행하지 않는다.
3. 실제 적용 시각과 설정을 다음 시도에 연결한다.
4. 재보정·재시작·외부 수동 변경은 별도 사건으로 남긴다.

## 4. 입력 계약

| 입력 타입 | 필수 의미 |
| --- | --- |
| ApplicationAck 또는 ClientStateProbe | 명령 ID·실제 값·epoch |
| CommandTicket | 원래 변경 묶음과 전제 |
| SessionState | 대기·확정된 버전 |

세션·시도·시계·버전 참조는 [데이터 모델](../05-contracts/data-models.md)에 따른다. 범위가 맞지 않거나 필수 필드가 없으면 추정값으로 채우지 않는다.

## 5. 출력 계약

반환은 `NodeResult[InterventionRecord]`이며 `status`, `data`, `diagnostics`, `outcome` 네 키를 사용한다.

- `data` 타입: `InterventionRecord`
- 보존할 업무 필드: `intervention_id, command_ref, requested_values, actual_values, lifecycle, effective_attempt_ref, reconciliation_reason`
- `diagnostics`는 위 내부 함수명을 키로 실행·생략·실패와 근거를 기록한다.
- 데이터의 `null`, 빈 목록, unknown은 서로 다른 의미다. [공통 결과 계약](../05-contracts/common-result.md)의 규칙을 따른다.

## 6. 업무 결과와 오류

| outcome | 업무상 의미 |
| --- | --- |
| intervention_confirmed | 실제 적용 확인 |
| intervention_rejected | 변경 없음 확인 |
| reconciliation_required | 실제 상태 불명 |
| ack_conflict | 요청과 ACK가 맞지 않음 |

`outcome`은 `status`와 다른 축이다. 정상적으로 보류·빈 결과·정보 부족을 판단했으면 `status=success`일 수 있다. 실제 필수 처리 실패는 `status=error`로 구분하고, 안전한 일부 산출물이 있을 때만 `partial`을 사용한다. 예외를 잡았다는 이유로 성공으로 바꾸지 않는다.

재시도 가능성은 진단 힌트로 반환하며, 실제 재시도·다음 단계 선택은 하네스가 판단한다. 대기나 비동기 실행을 실행 오류와 혼동하지 않는다.

## 7. 검증 사례

- ACK가 늦게 와도 다른 명령의 성공으로 연결하지 않는다.
- 서버의 만료 판단 뒤 클라이언트 적용이 발견되면 실제 값으로 조정한다.
- requested와actual 값을 모두 보존한다.
- 보고서가 불명·거절 상태를 실행 완료로 표현하지 않는다.

## 8. 설계 검토 항목

- 필드 타입·단위·버전과 유효 구간을 팀 계약에 맞춰 고정한다.
- 실행 한도·정책값은 [결정 항목](../07-decision-points.md)의 측정 절차로 선택한다.
- 근거·실행 상태·보류 사유가 다음 단계에서 소실되지 않는지 확인한다.

이 문서는 구현 책임과 검증 기준을 정의하며 현재 코드·완료율·구현 진척을 기록하지 않는다.
