# T-10 · `request_recalibration` — 재보정 요청과 평가 대기 제안

[도구 목록](README.md) · [공통 결과](../05-contracts/common-result.md) · [명령 프로토콜](../05-contracts/command-protocol.md)

## 1. 목적·호출 경계

좌표·자세 기준이 유효하지 않을 때 사용자 보정 절차로 전환하도록 준비한다.

- 모드: `stage`
- 연결된 세부 계약: [S-03](../03-small-nodes/S-03.md) · [S-04](../03-small-nodes/S-04.md) · [S-11](../03-small-nodes/S-11.md) · [S-12](../03-small-nodes/S-12.md) · [S-13](../03-small-nodes/S-13.md) · [S-14](../03-small-nodes/S-14.md) · [S-15](../03-small-nodes/S-15.md)
- 제한: LLM이 직접 보정 샘플을 만들거나 새 보정 유효성을 선언할 수 없다. 이 제안은 다른 설정 변경과 혼합하지 않는다.
- 모든 예시 값은 구조 설명용이며 측정 결과가 아니다.

## 2. 호출 전제와 권한

- 관측 품질 근거 또는 사용자의 보정 요청이 있어야 한다.
- 입력 평가 보류가 필요한 경우 시스템은 이 도구와 독립적으로 즉시 보류한다.

세션·시도 범위, snapshot_ref, tool_call_id, 버전·예산은 하네스가 검증한다. 모델의 reason 문장은 권한·유효성의 증거를 대체하지 않는다.

## 3. 모델 입력 인자

| 인자 | 타입 | 필수 | 의미 |
| --- | --- | --- | --- |
| scope | string | 예 | 다시 수집할 기준 |
| reason | string | 예 | 품질 근거에 연결된 보정 이유 |

### JSON Schema

```json
{
  "type": "object",
  "properties": {
    "scope": {
      "type": "string",
      "description": "다시 수집할 기준",
      "minLength": 1,
      "enum": [
        "geometry",
        "pose",
        "both"
      ]
    },
    "reason": {
      "type": "string",
      "description": "품질 근거에 연결된 보정 이유",
      "minLength": 1
    }
  },
  "required": [
    "scope",
    "reason"
  ],
  "additionalProperties": false
}
```

### 호출 예시

```json
{
  "name": "request_recalibration",
  "arguments": {
    "scope": "pose",
    "reason": "손 선택 변경 이후 기존 자세 기준을 사용할 수 없음"
  }
}
```

범위·버전·두 필드 간 관계·운영 한도는 스키마 외의 의미 검증으로 확인한다. 파싱 성공만으로 실행 가능하다고 판단하지 않는다.

## 4. 내부 함수와 처리 순서

| 함수 | 입력 | 책임 |
| --- | --- | --- |
| resolve_recalibration_scope | 품질 근거·scope | 수집 범위 |
| stage_recalibration_request | 사유·현재 기준 | 보정 전환 제안 |
| define_recovery_conditions | 보정 종류 | 유효한 새 기준·재개 조건 |

1. 문제 범위가 자세·기하·둘 다인지 확인한다.
2. 보정 안내로의 제어 전환을 stage한다.
3. 적용 ACK 이후에도 사용자 수집·새 CalibrationBundle이 확보될 때까지 완료를 선언하지 않는다.

## 5. 반환 계약과 예시

반환 타입: `NodeResult[ActionProposal]`. 진단은 실제 수행한 단계별로 기록한다. 다음 예시는 대표 필드만 보여준다.

```json
{
  "status": "success",
  "data": {
    "proposal_id": "proposal-example-01",
    "operation": "request_recalibration",
    "arguments": {
      "scope": "pose",
      "reason": "손 선택 변경 이후 기존 자세 기준을 사용할 수 없음"
    },
    "snapshot_ref": "snap-a03",
    "lifecycle": "staged",
    "actual_setting_changed": false
  },
  "diagnostics": {
    "resolve_recalibration_scope": {
      "status": "success"
    }
  },
  "outcome": "action_staged"
}
```

`action_staged`는 제안 저장에 성공했다는 뜻이다. S-12의 최종 검증·S-13의 명령 발행·S-14의 실제 적용·S-15의 대조 전에는 UI가 바뀌지 않는다. 같은 계획의 여러 설정 제안은 하나의 원자 change_set으로 묶는다. 제어 전환 도구와 설정 변경을 혼합하지 않는다.

## 6. 실패·보류 처리

| 코드 | 조건 | 처리 |
| --- | --- | --- |
| RECALIBRATION_ALREADY_PENDING | 이미 보정 대기 | 기존 보정 상태 반환 |
| INVALID_RECALIBRATION_SCOPE | 지원 범위 밖 | 지원 scope로 수정 |
| USER_CANCELLED_CALIBRATION | 사용자가 중단 | 자동 재개하지 않음 |

업무상 정보 부족·정상 대기는 `status=success`와 별도 outcome으로 반환할 수 있다. 실행 실패는 `error`, 안전한 일부 결과를 보존할 때만 `partial`이다. 오류 코드는 `diagnostics`에, 업무 결과는 `outcome`에 둔다.

## 7. 부작용·멱등성·재시도

실제 설정 부작용은 검증된 change_set의 적용 단계에서만 발생한다. 동일 context_id + tool_call_id는 같은 proposal_id를 반환한다. 이후 명령 재전송은 command_id 기준으로 한 번만 적용한다. 오래된 상태의 제안을 조용히 새 설정에 덮어쓰지 않는다.

일시적 실행 오류는 공통 예산 내에서만 재시도한다. 범위·버전·사용자 의사 위반은 동일 입력으로 반복하지 않는다. 단계별 시간과 토큰·호출 사용량은 [하네스](../06-harness-and-evaluation.md)가 기록한다.

## 8. 검증 사례

- 요청 수락과 보정 완료를 구분한다.
- 구간 초기화를 보정 완료라고 표시하지 않는다.
- 새 버전 이전의 진행 탭 주기와 대기 명령을 무효화한다.

## 9. 확인할 로그

`run_id`, `context_id`, `tool_call_id`, 도구·계약 버전, 요청 snapshot_ref, 입력 인자, 결과·근거 ID, status·outcome, 지연, 예산 사용량을 남긴다. 변경 도구는 proposal_id에서 command_id·ACK·intervention_id까지 연결한다.

이 문서는 계획 명세다. 특정 모델이나 라이브러리의 자동 실행 기능을 전제로 하지 않으며 현재 구현 진척을 기록하지 않는다.
