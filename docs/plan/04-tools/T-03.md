# T-03 · `get_tracking_summary` — 관측 품질·실패 구간 조회

[도구 목록](README.md) · [공통 결과](../05-contracts/common-result.md) · [명령 프로토콜](../05-contracts/command-protocol.md)

## 1. 목적·호출 경계

카메라·추적·보정·손 연결·시간 공백의 상태와 평가 제외 이유를 조회한다.

- 모드: `read`
- 연결된 세부 계약: [S-04](../03-small-nodes/S-04.md)
- 제한: 품질이 나쁜 원인을 이미지 없이 확정할 수 없으면 가림·배치 원인을 추측하지 않는다.
- 모든 예시 값은 구조 설명용이며 측정 결과가 아니다.

## 2. 호출 전제와 권한

- 시도 시간 범위와 clock_id가 명확하고 start_ms < end_ms여야 한다.
- 프레임 수·시간·비율의 분모를 함께 제공한다.

세션·시도 범위, snapshot_ref, tool_call_id, 버전·예산은 하네스가 검증한다. 모델의 reason 문장은 권한·유효성의 증거를 대체하지 않는다.

## 3. 모델 입력 인자

| 인자 | 타입 | 필수 | 의미 |
| --- | --- | --- | --- |
| attempt_id | string | 예 | 같은 세션의 시도 ID |
| start_ms | number | 예 | 세션 clock_id 기준 시작 시각, 포함. 요청 시도 범위 안에서 사용 |
| end_ms | number | 예 | 세션 clock_id 기준 끝 시각, 미포함. 요청 시도 범위 안에서 사용 |

### JSON Schema

```json
{
  "type": "object",
  "properties": {
    "attempt_id": {
      "type": "string",
      "description": "같은 세션의 시도 ID",
      "minLength": 1
    },
    "start_ms": {
      "type": "number",
      "description": "세션 clock_id 기준 시작 시각, 포함. 요청 시도 범위 안에서 사용",
      "minimum": 0
    },
    "end_ms": {
      "type": "number",
      "description": "세션 clock_id 기준 끝 시각, 미포함. 요청 시도 범위 안에서 사용",
      "minimum": 0
    }
  },
  "required": [
    "attempt_id",
    "start_ms",
    "end_ms"
  ],
  "additionalProperties": false
}
```

### 호출 예시

```json
{
  "name": "get_tracking_summary",
  "arguments": {
    "attempt_id": "a03",
    "start_ms": 0,
    "end_ms": 3000
  }
}
```

범위·버전·두 필드 간 관계·운영 한도는 스키마 외의 의미 검증으로 확인한다. 파싱 성공만으로 실행 가능하다고 판단하지 않는다.

## 4. 내부 함수와 처리 순서

| 함수 | 입력 | 책임 |
| --- | --- | --- |
| validate_time_window | 시도·시각 범위 | 동일 시계의 유효 창 |
| aggregate_quality_signals | 품질 사건 | 원인별 지표 |
| preserve_unknown_intervals | 유효·무효 구간 | 제외 범위·reason |

1. 요청 창과 저장된 품질 근거의 시간 기준을 맞춘다.
2. 시간 공백·검출 누락·보정 상태를 분리한다.
3. 재보정이 필요한 이유와 단순 추가 관측 사유를 반환한다.

## 5. 반환 계약과 예시

반환 타입: `NodeResult[TrackingSummary]`. 진단은 실제 수행한 단계별로 기록한다. 다음 예시는 대표 필드만 보여준다.

```json
{
  "status": "success",
  "data": {
    "attempt_id": "a03",
    "window": {
      "start_ms": 0,
      "end_ms": 3000
    },
    "frame_count": 90,
    "usable_frame_count": 62,
    "last_new_frame_age_ms": 30,
    "unknown_intervals": [
      {
        "start_ms": 1200,
        "end_ms": 1800,
        "reason": "HAND_ASSOCIATION_AMBIGUOUS"
      }
    ],
    "quality_policy_version": "quality-v1",
    "quality_ref": "quality-a03",
    "quality_state": "hold_required"
  },
  "diagnostics": {
    "validate_time_window": {
      "status": "success"
    }
  },
  "outcome": "result_available"
}
```

목록이 없거나 비교 근거가 부족한 정상 결과와 저장소·모델 실행 실패를 구분한다. 반환할 수 없는 수치는 null과 사유로 남긴다. 실제 조회·계산 과정과 결과 ID를 진단·근거로 연결한다.

## 6. 실패·보류 처리

| 코드 | 조건 | 처리 |
| --- | --- | --- |
| CLOCK_SCOPE_MISMATCH | 다른 시계의 창 요청 | 올바른 로컬 시계로만 재호출 |
| QUALITY_UNAVAILABLE | 관측 품질 근거 없음 | unknown 유지 |
| INVALID_TIME_RANGE | 범위 역전·시도 밖 | 유효 창으로 수정 |

업무상 정보 부족·정상 대기는 `status=success`와 별도 outcome으로 반환할 수 있다. 실행 실패는 `error`, 안전한 일부 결과를 보존할 때만 `partial`이다. 오류 코드는 `diagnostics`에, 업무 결과는 `outcome`에 둔다.

## 7. 부작용·멱등성·재시도

사용자 연습 설정을 변경하지 않는다. 조회 재시도는 동일 snapshot_ref·조회 범위를 유지한다. 로그·캐시는 허용하지만 다른 시점의 결과로 바뀌었다면 snapshot·freshness를 명시한다.

일시적 실행 오류는 공통 예산 내에서만 재시도한다. 범위·버전·사용자 의사 위반은 동일 입력으로 반복하지 않는다. 단계별 시간과 토큰·호출 사용량은 [하네스](../06-harness-and-evaluation.md)가 기록한다.

## 8. 검증 사례

- 유효 프레임 비율이 높아도 영상 정지를 감지한다.
- 좌우 손 분류 점수를 접촉 확률로 설명하지 않는다.
- 일부 누락의 위치가 보존된다.

## 9. 확인할 로그

`run_id`, `context_id`, `tool_call_id`, 도구·계약 버전, 요청 snapshot_ref, 입력 인자, 결과·근거 ID, status·outcome, 지연, 예산 사용량을 남긴다. 변경 도구는 proposal_id에서 command_id·ACK·intervention_id까지 연결한다.

이 문서는 계획 명세다. 특정 모델이나 라이브러리의 자동 실행 기능을 전제로 하지 않으며 현재 구현 진척을 기록하지 않는다.
