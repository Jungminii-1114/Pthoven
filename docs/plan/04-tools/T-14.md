# T-14 · `inspect_visual_context` — 대표 프레임 시각 진단

[도구 목록](README.md) · [공통 결과](../05-contracts/common-result.md) · [명령 프로토콜](../05-contracts/command-protocol.md)

## 1. 목적·호출 경계

구조화 지표로 설명이 부족한 카메라 배치·잘림·가림을 제한된 대표 프레임으로 점검한다.

- 모드: `optional_read`
- 연결된 세부 계약: [S-10](../03-small-nodes/S-10.md) · [S-11](../03-small-nodes/S-11.md)
- 제한: 이 결과는 품질 정책이나 접촉 정답을 덮어쓰지 않는다. 기본 Agent에 이미지 이해 능력이 있어야 한다는 전제가 아니다.
- 모든 예시 값은 구조 설명용이며 측정 결과가 아니다.

## 2. 호출 전제와 권한

- 시각 진단 기능·프레임 보관·접근 정책이 명시적으로 허용되어야 한다.
- 메트릭 조회만으로 충분하면 호출하지 않는다.

세션·시도 범위, snapshot_ref, tool_call_id, 버전·예산은 하네스가 검증한다. 모델의 reason 문장은 권한·유효성의 증거를 대체하지 않는다.

## 3. 모델 입력 인자

| 인자 | 타입 | 필수 | 의미 |
| --- | --- | --- | --- |
| evidence_ids | array | 예 | 같은 세션에서 조회가 허용된 프레임 참조. 설계상 한 호출 최대 4개 |
| question | string | 예 | 관측 환경에 관한 좁은 질문 |

### JSON Schema

```json
{
  "type": "object",
  "properties": {
    "evidence_ids": {
      "type": "array",
      "description": "같은 세션에서 조회가 허용된 프레임 참조. 설계상 한 호출 최대 4개",
      "items": {
        "type": "string"
      },
      "minItems": 1,
      "maxItems": 4
    },
    "question": {
      "type": "string",
      "description": "관측 환경에 관한 좁은 질문",
      "minLength": 1
    }
  },
  "required": [
    "evidence_ids",
    "question"
  ],
  "additionalProperties": false
}
```

### 호출 예시

```json
{
  "name": "inspect_visual_context",
  "arguments": {
    "evidence_ids": [
      "frame-ref-21",
      "frame-ref-22"
    ],
    "question": "손끝이 화면 밖으로 잘리는 단서가 보이는가?"
  }
}
```

범위·버전·두 필드 간 관계·운영 한도는 스키마 외의 의미 검증으로 확인한다. 파싱 성공만으로 실행 가능하다고 판단하지 않는다.

## 4. 내부 함수와 처리 순서

| 함수 | 입력 | 책임 |
| --- | --- | --- |
| authorize_frame_refs | 컨텍스트·프레임 ID | 허용 프레임 |
| call_optional_visual_model | 제한 프레임·질문 | 시각 설명 |
| constrain_visual_findings | 설명·출처 | 잠정 근거·한계 |

1. 프레임 ID·세션·시각·보관·접근 범위를 확인한다.
2. 최소 프레임과 질문만 VLM에 전달한다.
3. 보이는 단서·잠정 해석·확인 불가 항목을 분리한다.

## 5. 반환 계약과 예시

반환 타입: `NodeResult[VisualInspection]`. 진단은 실제 수행한 단계별로 기록한다. 다음 예시는 대표 필드만 보여준다.

```json
{
  "status": "success",
  "data": {
    "findings": [
      {
        "claim": "두 대표 프레임에서 일부 손끝이 영상 경계에 가깝게 보임",
        "evidence_refs": [
          "frame-ref-21",
          "frame-ref-22"
        ],
        "certainty": "tentative"
      }
    ],
    "limitations": [
      "보이지 않는 접촉 면과 실제 접촉 여부는 확인할 수 없음"
    ],
    "contact_verified": false,
    "visual_model_ref": "vision-profile-example"
  },
  "diagnostics": {
    "authorize_frame_refs": {
      "status": "success"
    }
  },
  "outcome": "visual_findings_tentative"
}
```

목록이 없거나 비교 근거가 부족한 정상 결과와 저장소·모델 실행 실패를 구분한다. 반환할 수 없는 수치는 null과 사유로 남긴다. 실제 조회·계산 과정과 결과 ID를 진단·근거로 연결한다.

## 6. 실패·보류 처리

| 코드 | 조건 | 처리 |
| --- | --- | --- |
| VISUAL_INSPECTION_DISABLED | 선택 기능 비활성 | 도구 생략, 다른 조회로 진행 |
| VISUAL_EVIDENCE_EXPIRED | 프레임 참조 만료 | 없음을 꾸미지 않고 추가 관측 |
| VISUAL_MODEL_FAILED | VLM 호출 실패 | 선택 기능 실패 기록 |
| CONTACT_VERIFICATION_UNSUPPORTED | 실제 접촉 확정 요청 | 요청 거절·한계 설명 |

업무상 정보 부족·정상 대기는 `status=success`와 별도 outcome으로 반환할 수 있다. 실행 실패는 `error`, 안전한 일부 결과를 보존할 때만 `partial`이다. 오류 코드는 `diagnostics`에, 업무 결과는 `outcome`에 둔다.

## 7. 부작용·멱등성·재시도

사용자 연습 설정을 변경하지 않는다. 조회 재시도는 동일 snapshot_ref·조회 범위를 유지한다. 로그·캐시는 허용하지만 다른 시점의 결과로 바뀌었다면 snapshot·freshness를 명시한다.

일시적 실행 오류는 공통 예산 내에서만 재시도한다. 범위·버전·사용자 의사 위반은 동일 입력으로 반복하지 않는다. 단계별 시간과 토큰·호출 사용량은 [하네스](../06-harness-and-evaluation.md)가 기록한다.

## 8. 검증 사례

- 프레임이 없으면 시각 설명을 만들지 않는다.
- 손등 영상에서 접촉 확률·압력·높이를 확정하지 않는다.
- VLM 실패가 유효한 텍스트 코칭을 중단시키지 않는다.

## 9. 확인할 로그

`run_id`, `context_id`, `tool_call_id`, 도구·계약 버전, 요청 snapshot_ref, 입력 인자, 결과·근거 ID, status·outcome, 지연, 예산 사용량을 남긴다. 변경 도구는 proposal_id에서 command_id·ACK·intervention_id까지 연결한다.

이 문서는 계획 명세다. 특정 모델이나 라이브러리의 자동 실행 기능을 전제로 하지 않으며 현재 구현 진척을 기록하지 않는다.
