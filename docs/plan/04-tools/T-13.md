# T-13 · `finish_practice` — 연습 종료와 보고서 요청 제안

[도구 목록](README.md) · [공통 결과](../05-contracts/common-result.md) · [명령 프로토콜](../05-contracts/command-protocol.md)

## 1. 목적·호출 경계

사용자가 종료하거나 사전 정의한 종료 조건이 충족되면 세션 마감과 보고서 생성을 준비한다.

- 모드: `stage`
- 연결된 세부 계약: [S-11](../03-small-nodes/S-11.md) · [S-12](../03-small-nodes/S-12.md) · [S-13](../03-small-nodes/S-13.md) · [S-14](../03-small-nodes/S-14.md) · [S-15](../03-small-nodes/S-15.md) · [S-18](../03-small-nodes/S-18.md) · [S-19](../03-small-nodes/S-19.md)
- 제한: 이 도구가 보고서를 작성·검증하는 것은 아니다. 마감이 확인된 뒤 별도 보고서 단계가 수행된다.
- 모든 예시 값은 구조 설명용이며 측정 결과가 아니다.

## 2. 호출 전제와 권한

- 실제 종료 요청 사건 또는 명시한 종료 정책이 있어야 한다.
- 진행 중 입력·미해결 명령·unknown 적용 상태를 먼저 정리한다.

세션·시도 범위, snapshot_ref, tool_call_id, 버전·예산은 하네스가 검증한다. 모델의 reason 문장은 권한·유효성의 증거를 대체하지 않는다.

## 3. 모델 입력 인자

| 인자 | 타입 | 필수 | 의미 |
| --- | --- | --- | --- |
| reason | string | 예 | 사용자 종료 또는 종료 조건 근거 |

### JSON Schema

```json
{
  "type": "object",
  "properties": {
    "reason": {
      "type": "string",
      "description": "사용자 종료 또는 종료 조건 근거",
      "minLength": 1
    }
  },
  "required": [
    "reason"
  ],
  "additionalProperties": false
}
```

### 호출 예시

```json
{
  "name": "finish_practice",
  "arguments": {
    "reason": "사용자가 이번 연습을 마치고 결과를 보기로 선택함"
  }
}
```

범위·버전·두 필드 간 관계·운영 한도는 스키마 외의 의미 검증으로 확인한다. 파싱 성공만으로 실행 가능하다고 판단하지 않는다.

## 4. 내부 함수와 처리 순서

| 함수 | 입력 | 책임 |
| --- | --- | --- |
| verify_finish_intent | 종료 사건·정책 | 마감 권한 |
| define_session_close_boundary | 진행 시도·명령 | 종료 경계 |
| stage_finish_action | 종료 근거 | 마감 제안·보고서 요청 범위 |

1. 종료 근거와 마감 범위를 검사한다.
2. 완료된 구간·중단 구간을 구분해 종료를 stage한다.
3. 실제 마감 확인 후 B-07의 보고서 흐름에 사건을 전달한다.

## 5. 반환 계약과 예시

반환 타입: `NodeResult[ActionProposal]`. 진단은 실제 수행한 단계별로 기록한다. 다음 예시는 대표 필드만 보여준다.

```json
{
  "status": "success",
  "data": {
    "proposal_id": "proposal-example-01",
    "operation": "finish_practice",
    "arguments": {
      "reason": "사용자가 이번 연습을 마치고 결과를 보기로 선택함"
    },
    "snapshot_ref": "snap-a03",
    "lifecycle": "staged",
    "actual_setting_changed": false
  },
  "diagnostics": {
    "verify_finish_intent": {
      "status": "success"
    }
  },
  "outcome": "action_staged"
}
```

`action_staged`는 제안 저장에 성공했다는 뜻이다. S-12의 최종 검증·S-13의 명령 발행·S-14의 실제 적용·S-15의 대조 전에는 UI가 바뀌지 않는다. 같은 계획의 여러 설정 제안은 하나의 원자 change_set으로 묶는다. 제어 전환 도구와 설정 변경을 혼합하지 않는다.

## 6. 실패·보류 처리

| 코드 | 조건 | 처리 |
| --- | --- | --- |
| FINISH_INTENT_REQUIRED | 종료 근거 없음 | 계속 또는 사용자 요청 대기 |
| COMMAND_STATE_UNKNOWN | 실제 설정 불명 | 상태 조정 후 종료 |
| SESSION_ALREADY_CLOSED | 이미 마감됨 | 기존 종료·보고서 참조 반환 |

업무상 정보 부족·정상 대기는 `status=success`와 별도 outcome으로 반환할 수 있다. 실행 실패는 `error`, 안전한 일부 결과를 보존할 때만 `partial`이다. 오류 코드는 `diagnostics`에, 업무 결과는 `outcome`에 둔다.

## 7. 부작용·멱등성·재시도

실제 설정 부작용은 검증된 change_set의 적용 단계에서만 발생한다. 동일 context_id + tool_call_id는 같은 proposal_id를 반환한다. 이후 명령 재전송은 command_id 기준으로 한 번만 적용한다. 오래된 상태의 제안을 조용히 새 설정에 덮어쓰지 않는다.

일시적 실행 오류는 공통 예산 내에서만 재시도한다. 범위·버전·사용자 의사 위반은 동일 입력으로 반복하지 않는다. 단계별 시간과 토큰·호출 사용량은 [하네스](../06-harness-and-evaluation.md)가 기록한다.

## 8. 검증 사례

- 모델이 저조한 성적을 숨기기 위해 세션을 종료하지 못한다.
- 중간 취소를 성공적인 연습 완료로 쓰지 않는다.
- 보고서 생성 실패가 연습을 다시 활성화하지 않는다.

## 9. 확인할 로그

`run_id`, `context_id`, `tool_call_id`, 도구·계약 버전, 요청 snapshot_ref, 입력 인자, 결과·근거 ID, status·outcome, 지연, 예산 사용량을 남긴다. 변경 도구는 proposal_id에서 command_id·ACK·intervention_id까지 연결한다.

이 문서는 계획 명세다. 특정 모델이나 라이브러리의 자동 실행 기능을 전제로 하지 않으며 현재 구현 진척을 기록하지 않는다.
