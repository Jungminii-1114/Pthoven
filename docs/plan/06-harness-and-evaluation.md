# 하네스·실행 기록·평가 계획

[문서 안내](README.md) · [도구](04-tools/README.md) · [공통 계약](05-contracts/README.md)

## 1. 하네스의 역할

하네스는 모델을 둘러싸고 상태·호출·도구·명령·오류·기록·평가를 일관되게 관리하는 실행 계층이다. 특정 프레임워크나 다중 Agent 구성을 의미하지 않는다.

| 구성 | 책임 | 연결 |
| --- | --- | --- |
| Trigger controller | 사건 중복·우선순위·동시 실행 제어 | S-09 |
| Context builder | 상태·근거·관련 이력·허용 도구 선택 | S-10 |
| Model adapter | 모델·런타임별 요청·도구 응답 변환 | S-11, S-18 |
| Tool registry | 도구 스키마·조회·제안 stage 함수 연결 | T-01~T-14 |
| Plan validator | 스키마·근거·최종 설정·전제 조건 검사 | S-12 |
| Command coordinator | 중복 방지·원자 적용·ACK·불명 상태 조정 | S-13~S-15 |
| State store | 불변 스냅샷과 실제 설정·개입 이력 | S-08, S-15 |
| Trace recorder | 입력·결정·도구·실행·시간·비용 기록 | 모든 경로 |
| Replay evaluator | 동일 입력으로 정책·모델 비교 | 평가 전용 |

프레임 처리 루프와 모델 판단은 분리한다. 품질 보류는 모델 호출 없이 실행할 수 있어야 한다. 무거운 모델 사용으로 영상 처리 품질이 떨어지는지도 전체 경로에서 측정한다.

## 2. 한 번의 코칭 실행

1. 새 사건과 스냅샷을 확인하고 동시 판단 실행권을 확보한다.
2. 필수 품질 보류는 즉시 수행하고 command_epoch를 갱신한다.
3. 관련 근거·허용 도구·사용자 요청·남은 예산을 모델에 제공한다.
4. 읽기 도구는 범위 내에서 실행하고 결과를 모델에 반환한다.
5. 변경 도구는 제안만 stage하고 actual 설정을 바꾸지 않는다.
6. 최종 계획의 근거·인자·상태·단계·사용자 의사를 검증한다.
7. 명령을 발행하고 적용 경계·ACK를 기다린다. 모델 응답만으로 완료 처리하지 않는다.
8. 실제 적용 결과를 상태에 연결하고 다음 시도 종료 사건을 기다린다.
9. 비교 결과가 새 근거를 제공할 때 다음 판단을 시작한다.

루프 안의 ‘정보 조회’와 사용자 재연주를 기다리는 ‘시간에 걸친 재평가’는 다르다. 새 연주가 없는데 모델을 반복 호출해 개선을 만들어내지 않는다.

## 3. 예산과 실패 복구

| 예산 | 설정 단위 | 선택 기준 |
| --- | --- | --- |
| 관측 공백·보정 수집 | QualityPolicy | 실제 장치·프레임 속도·실패 데이터 |
| 모델 전체 시간 | CoachRunPolicy | 허용 가능한 체험 대기와 p50·p95 지연 |
| 입력·출력·추론 토큰 | ModelProfile | 근거 누락 여부·지연·보고서 품질 |
| 도구 호출 수·반환 크기 | ToolPolicy | 필요한 조회 깊이와 반복 방지 |
| 형식 수정·일시 오류 재시도 | RetryPolicy | 오류 종류·같은 전제 유지 여부 |
| 명령 유효 시간·ACK 대기 | CommandPolicy | 실제 전달·경계 대기·재연결 측정 |

숫자 한도는 팀 결정 항목으로 고정하고 버전을 남긴다. T-04의 조회 최대 20개, T-14의 대표 프레임 최대 4개는 초기 인터페이스 제안이며 물리 성능 수치가 아니다. 필요하면 계약 버전 변경으로 조정한다.

필수 모델 실행이 실패하면 마지막으로 확인된 설정을 유지한다. 관측이 나쁘면 평가 보류를 유지한다. 규칙 정책·템플릿으로 대체했다면 출처를 표시한다. 범위·버전·사용자 의사 위반은 같은 인자로 재시도하지 않는다.

## 4. 모델·런타임 선택

텍스트 모델, 실행 도구, 하네스는 독립적으로 교체한다. 예를 들어 R1·Qwen·Gemma 계열을 로컬에서 비교하거나 외부 API를 비교할 수 있다. 기본 판단에 VLM이 필수는 아니다.

비교 시 model_id·revision/digest·양자화·런타임·chat template·프롬프트·생성 설정·지원 도구·스키마를 함께 기록한다. 같은 이름의 이동 태그를 고정된 실험 모델로 간주하지 않는다. 추론 모델의 긴 응답이나 일반 벤치마크 점수는 한국어 코칭·도구 선택의 우수성을 보장하지 않는다.

모델 어댑터는 제공자 고유 tool_calls를 ToolCallRequest로, 최종 응답을 CoachPlan 또는 ReportDraft로 변환한다. 파서가 이해하지 못한 도구 형식을 문자열 패턴으로 억지 실행하지 않는다.

## 5. 기록할 실행 추적

run_id, parent_run_id, 세션·시도·snapshot_ref, trigger_ref, 단계·도구·계약 버전, 모델 설정, input artifact refs, NodeResult, proposal_id, command_id, ACK·intervention_id, 지연·예산·비용, output artifact refs를 연결한다.

관측·정렬·지표·계획·실제 적용·비교·검증된 보고서를 따라가며 ‘어떤 근거로 왜 무엇을 실제로 바꿨는가’를 설명할 수 있어야 한다. raw 영상 저장과 구조화 이벤트 로그 저장은 별도 정책으로 선택한다.

실행 로그에 정답이 자동으로 생기는 것은 아니다. 독립 검토한 물리 접촉 라벨, 사람의 전략 타당성 평가, 단순 실행 성공을 구분한다.

## 6. CV 평가

초기 수집은 고정된 카메라·책상·조명에서 한 손 검지로 수행한다. 한 trial에 정지·단일 탭·반복 탭·끌기·공중 탭 중 하나만 넣고 시행 ID·조건·실패를 보존한다. 확장 조건은 손 전체 이동·이웃 손가락·가림·조명·카메라 위치다.

### 수집·라벨 절차

1. 익명 person_id·session_id, 장치·각도·조명·프레임 상태를 기록한다.
2. 기준·들림 자세를 별도 수집하고 보정 자료와 평가 시행을 구분한다.
3. 조건별 짧은 시행을 반복하고 실제 수행 횟수·예외를 기록한다.
4. 접촉을 평가하려면 독립 검토가 가능한 영상과 동기화 기준을 확보한다. 위쪽 영상만으로 불명확한 구간은 unknown으로 둔다.
5. 예측 이벤트·안내 시각을 정답 라벨로 복사하지 않는다.
6. 사람·세션 단위로 학습·검증·평가를 분리한다. 인접 프레임 무작위 분할로 일반화를 주장하지 않는다.

정밀도·재현율·F1·오입력/분·시간 오차와 함께 관측 가능 범위·보류율·프레임 손실을 보고한다. 보류율만 높여 오입력을 줄인 모델을 ‘정확하다’고 평가하지 않는다. 합성 관절의 상태 머신 검증과 실제 RGB 접촉 판정을 분리한다.

## 7. Agent·도구 평가

동일 스냅샷·조회 결과·사용자 의사·상태 변화 시나리오를 저장해 규칙 정책과 모델을 비교한다. 저장된 시나리오가 실제 수집인지 설계된 가상 상태인지 표시한다.

| 시험 상황 | 확인할 행동 |
| --- | --- |
| 관측 안정·같은 구간 어려움 반복 | 관련 구간·이력 조회 후 근거 있는 개입 |
| 관측 손실과 높은 오류 수 | 사용자 탓·불필요한 속도 감소보다 평가 보류·복구 우선 |
| 사용자 안정 수행 | 불필요한 개입 없이 유지·목표에 맞는 힌트 조절 |
| 낮춘 템포에서 점수 상승 | 조건 차이를 명시하고 원래 템포 향상 단정 금지 |
| 후보 수는 있으나 정렬 불가 | 지표·전략의 확신을 낮추고 추가 관측 |
| 사용자가 수동 정지·설정 변경 | 오래된 계획 거절, 자동 재개 방지 |
| 모델이 잘못된 인자·근거 생성 | 실행 거절, 제한된 수정 또는 안전한 대체 |
| 변경 후 ACK 누락 | 실제 상태 조회, 성공·실패 단정 금지 |
| 조회·모델 장애 | 없는 정보를 0으로 채우지 않고 출처 표시 |

형식 통과율, 등록 도구·인자 유효율, 근거 없는 주장, 수치·상태 일치, 전략 타당성, 불필요한 개입, 보고서 이해도, 지연·자원을 평가한다. 같은 입력에서 같은 문장을 쓰는 비율만 측정하지 않는다. 복수의 적절한 전략을 허용하고 사람 평가 기준을 먼저 정한다.

모델이 자신의 결과를 채점한 점수만을 최종 품질로 사용하지 않는다. 수치·실행 검증은 코드로, 교육적 타당성과 명료성은 기준이 있는 검토로 평가한다.

## 8. 실행 프로토콜 평가

S-13~S-15는 모델 없이도 시험할 수 있어야 한다. 지연·중복·순서 바뀜·ACK 유실·재연결·수동 변경·부분 인자 오류·만료·서버 복구를 주입해 실제 설정과 기록이 일치하는지 확인한다.

모든 오류를 정상 상황으로 감추는 것이 목표가 아니다. 실제로 알 수 없는 적용 상태를 unknown으로 남기고 상충 작업을 막을 수 있어야 한다.

## 9. 데모와 UI

기본 체험은 짧은 구간 한 번, 코치의 근거·선택·실제 변경 확인, 한 번의 재도전, 조건부 비교다. 길이는 실제 사용자 체험으로 정한다.

디자인은 프리뷰, 보정 안내, 입력 보류, 코치 조회 중, 제안 준비, 적용 대기, 적용 확인, 비교 제한, 다음 연습을 구분한다. 내부 함수명·모델 추론 전문을 사용자 화면에 그대로 보여줄 필요는 없다.

짧은 체험에서 재연주가 어렵다면 저장 세션 재생으로 개입 전후를 보여준다. live / real-capture replay / synthetic demo를 표시하고 참가자 연주로 오인시키지 않는다. 실제 사용자는 잘 연주했는데 데모를 위해 오류를 강제로 만들지 않는다.
