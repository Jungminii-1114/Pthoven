## 1. 곡 선정

### 1.1 데이터
- 출처는 11/6에 만든 로컬 전처리 결과(`Pthoven_preprocessed_2026-11-06`)다. 저장소에는 올리지 않는다.
- **nASAP는 쓰지 않았다.** 대응 악보 187개가 모두 바흐 푸가, 베토벤 소나타 같은 연주회용 곡이다. 전부 기본 지원 조건(C4~C5, 단음, 초당 4음)을 넘는다(`ready=false`).
- **Mutopia**에서는 516곡의 reference 음표를 전부 훑었다. 이조 한 번으로 흰 건반 C4~C5 안에 단음으로 들어오는 4·8마디 구간이 1,042개였고, 여기에 아래 기준을 더 적용해 3곡을 골랐다. 탐색 스크립트는 로컬 경로를 읽으므로 저장소 밖(작업 노트 폴더의 `pthoven-scripts/mutopia_easy_scan.py`)에 두었다.

### 1.2 선정 기준
데모 조건(검지·중지 위주, 느린 템포, 한 번에 한 음)에 맞췄다.

1. 오른손 트랙(평균 음높이가 가장 높은 트랙)의 같은 시각 최상음만 선율로 본다.
2. 곡의 **처음부터 시작하는** 4마디 또는 8마디 구간만 후보로 한다. 곡 중간에서 시작하면 사용자가 곡을 알아보기 어렵다.
3. 반음 이조 한 번으로 모든 음이 **흰 건반 C4~G4(도~솔, 5개)** 안에 들어와야 한다. 손을 옮기지 않는 5손가락 위치다.
4. 음 사이 간격이 4분음표 이상이어야 한다. 60 BPM에서 1초, 50 BPM에서 1.2초다. 우리 판정기는 손가락을 들었다 돌아와야 후보를 만들기 때문에 간격이 넉넉해야 한다.
5. 큰 도약이 적고, 같은 건반 반복이 있어도 된다. 같은 손가락 반복 탭은 검지 기록에서 가장 잘 검증된 경우다(capture-6·7, 10/10/10).

## 2. 변환 경로

```text
Mutopia MIDI ─ preprocess_mutopia.py ─▶ practice JSON (ready 검사) ─ export_song_chart.py ─▶ vision/web/songs/*.json
```

- 전처리 옵션(세 곡 공통): `--tracks 1 --melody highest --low 60 --high 67 --white-only --bpm 60 --max-polyphony 1 --max-density 2`. 곡마다 `--start-measure 1 --end-measure N --transpose S`를 준다.
- 세 곡 모두 `ready=true`, 최대 동시음 1, 1초 최대 밀도 1이다.
- **신규** `demo_test/preprocessing/export_song_chart.py`
  - practice JSON의 음을 **음높이·시각을 바꾸지 않고** 옮긴다. 건반 이름과 출처 표기만 붙인다.
  - `ready=false`, 데모 건반(흰 건반 C4~C5) 밖의 음, 동시음을 거부한다. vision `geometry.py`의 건반이 이 8개다.
  - `--end-quarter`로 자른 음은 ID를 기록한다.
  - 차트에 원본 MIDI SHA256, 전처리기 버전, practice `version_id`, `evaluation_policy`(onset만 비교)를 남긴다.
  - 실행할 때마다 `index.json`을 다시 만든다.

재생성(demo_test 폴더, Mutopia 요구사항을 설치한 가상환경):

```bash
python preprocessing/preprocess_mutopia.py --input <곡 폴더> --output <출력> --manifest <곡 manifest> \
  --tracks 1 --melody highest --low 60 --high 67 --white-only --bpm 60 --max-polyphony 1 --max-density 2 \
  --start-measure 1 --end-measure 4 --transpose -7
python preprocessing/export_song_chart.py --practice <출력>/<곡>.json --id pleyel-rondo-m1-4 --level 1 \
  --title-ko "플레옐 「론도」 첫 4마디" --output-dir ../vision/web/songs
```

manifest의 `midi_path`는 `--input` 폴더 기준이다. 곡 하나만 변환할 때는 곡 폴더 안에 그 곡만 담은 manifest를 둬야 출처 URL이 채워진다(처음에 공용 manifest를 줬다가 `source_url=null`이 된 것을 고쳤다).

## 3. 화면(`vision/web`)

### 3.1 구조
- **`practice.js`(신규):** 가이드 계산과 그리기를 `app.js`와 분리했다. 순수 함수는 `validateChart`, `schedule`, `layout`, `countdown`이고, `createGuide`가 캔버스 그리기와 실행 상태를 맡는다.
- **`index.html`:** 프리뷰 위에 `practice-overlay` 캔버스와 **8번 연습곡 가이드** 카드(곡, 템포 50/60/66/72, 시작·정지, 진행, 기록 저장, 출처)를 추가했다.
- **`app.js`:** 곡 목록과 차트 로드, 버튼 연결, 진행 표시만 추가했다. B-02 `handleInput`에서는 제안을 받은 그대로 `practice.guide.noteInput`에 넘긴다.

### 3.2 동작
- **시각:**
  - 기대 시각 = 가이드 시작 시각 t0 + onset_quarter × (60000 / BPM).
  - t0 = 시작 버튼 시각 + max(한 마디 카운트인, 낙하 시간 2.6초)다. 카운트인 동안 클릭음이 나고 화면에 남은 박을 표시한다.
- **위치:**
  - 타일 아랫변이 **가상 건반 윗변에 닿는 순간이 기대 시각**이다.
  - 열은 B-01 건반 영역(`keyboard-guide`의 화면 좌표)을 8등분한 위치다. 화면 반전과 상관없이 표시 좌표를 쓴다. B-02 매핑과 같은 화면 기준이다.
  - 타일 길이는 음 길이에 비례한다. 다음 음의 건반 열은 은은하게 강조한다.
- **입력 표시:**
  - B-02 `accepted_provisional` 입력은 해당 건반 윗변에 짧은 원으로 표시한다.
  - 보류 입력은 표시 없이 기록만 한다.
  - 관측 입력을 기대 음 쪽으로 옮기거나 고치지 않는다(PRD 3, 전체 계획 "기대 악보 음으로 관측 음을 채우지 않는다").
- **기록:** `pthoven-guide-run.v1` JSON에 아래 내용을 저장한다. B-03 정렬을 오프라인으로 개발할 때 입력 자료로 쓸 수 있다.
  - 곡과 출처, BPM, t0
  - 기대 음(시작·끝 ms)
  - 관측 입력(event_id, 손가락, 건반, 상태, t_ms, t0 기준 오프셋)
- **시계:** 모두 `performance.now()` 기준이다. B-02 사건의 `t_ms`(복귀 프레임 브라우저 시각)와 같은 시계라 오프셋을 그대로 계산할 수 있다. 판정 시각은 `emitted_ms`가 아니라 `t_ms` 기준이다.
- 카메라나 보정 없이도 가이드만 재생할 수 있다(화면 확인용).

### 3.3 함께 고친 기존 문제
- **증상:** 카메라와 세션이 없을 때 가상 건반 가이드의 폭이 0으로 남아 가이드 타일이 그려지지 않았다.
- **원인:** 첫 `updateGeometryUI()`가 레이아웃 전(프리뷰 폭 0)에 실행된다. 크기 변경 감지는 세션이 있을 때만 다시 계산했다.
- **수정:** 세션이 없으면 크기 변경 때 화면 표시만 다시 계산한다. 서버 기하 동기화 조건은 바꾸지 않았다.

## 4-1. 실사용 피드백 반영(같은 날, 카메라 확인 후)

사용자가 실제 카메라 화면에서 확인한 결과, 타일과 건반 칸 정렬은 맞았다. 다음 두 가지를 고쳤다.

| 피드백 | 변경 | 이유·버린 대안 |
|---|---|---|
| 따라 치기에 조금 느림 | 템포 선택지를 40/50/**60** → 50/60/**66**/72로 바꿨다. 기본값은 50 → **66**이다. | "약간만" 빠르게라는 요청이라 기본을 약 30% 올렸다. 72 BPM에서도 음 간격이 0.83초 이상이다. 들었다 돌아오는 사이클 시간 안이다. 90 이상은 넣지 않았다. |
| 건반 아래로도 내려오는 타일이 보임 | 타일을 **건반 윗변(판정선)에서 자른다**. 건반 안과 아래에는 그리지 않는다. 대신 음이 울리는 동안(기대 시각 ~ 끝) 해당 **건반 칸을 곡 색으로 채운다.** | 피아노 타일 게임의 판정선 방식이다. 건반 아랫변에서 자르는 방법도 있었지만, 건반 칸 안에 타일이 겹쳐 B-02 입력 원 표시와 칸 글자를 가렸다. 그래서 윗변에서 잘랐다. 기대 시각 정의(타일 아랫변 = 건반 윗변)는 그대로다. |

- `layout()`은 판정선 아래 부분을 잘라 반환하고, 판정선을 완전히 지난 타일은 반환하지 않는다(`past` 상태 삭제).
- `activeNotes()`를 추가했다.
- 테스트 1개를 추가했다(판정선 아래로 그려지는 타일 없음, 음이 끝나면 사라짐). 가이드 테스트는 9개, 웹 테스트 합계 31개가 통과한다.
- 브라우저에서 슈만 곡 66 BPM으로 확인했다. 타일이 판정선에서 사라지고 칠 건반 칸이 채워졌다.
